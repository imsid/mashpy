Pilot: a self-hosted app store built with Mash

Pilot is the reference application for the Mash SDK. The pool is the catalog, agents are the listings, host compositions are the installed apps, and a terminal CLI is the storefront. Here's how it's built.

What Pilot does

Pilot ships a catalog of agents the user can browse, compose into teams, and enter from a terminal. Its featured application is a guide to the Mash codebase with two agents. The pilot agent answers questions from the source. The builder agent builds Mash apps in the user's sandbox and checks that they work. The user composes which agents work together, then enters the REPL.

It also serves as the application behind the Mash documentation series, so framework features are observable in a real running system: agent processes, per-user sandboxes, delegation through the host's relay, host composition at runtime, durable workflows, skills, and traces.

The catalog

Every agent the store ships is a CatalogEntry in pilot/catalog/__init__.py. Each entry pairs a spec class with a metadata factory that returns the AgentMetadata for that agent's listing.

# pilot/catalog/__init__.py
@dataclass(frozen=True)
class CatalogEntry:
    agent_id: str
    create_spec: Callable[[], AgentSpec]
    build_metadata: Callable[[], AgentMetadata]

CATALOG: tuple[CatalogEntry, ...] = (
    CatalogEntry(pilot.PILOT_AGENT_ID, pilot.PilotSpec, pilot.build_metadata),
    CatalogEntry(builder.BUILDER_AGENT_ID, builder.BuilderSpec, builder.build_metadata),
)

build_pool() in pilot/spec.py registers each entry, the changelog workflow, and the default guide host. HostBuilder adds masher's eval agents and workflows to every pool.

# pilot/spec.py
def build_pool() -> Pool:
    builder = HostBuilder()
    for entry in CATALOG:
        builder.agent(entry.create_spec(), metadata=entry.build_metadata())
    builder.workflow(build_changelog_workflow_spec())
    builder.host(
        Host(
            host_id="guide",
            primary="pilot",
            subagents=("builder",),
            workflows=("pilot-changelog",),
        )
    )
    return builder.build()

Further hosts belong to the CLI's config file (~/.pilot/hosts.json) and are published to the deployment as idempotent PUTs when the CLI connects.

Agent processes and sandboxes

Every agent runs as a process of the host, inside its container. The bash commands an agent's model writes run somewhere else: in the sandbox of the user the request acts for, a mash-sandbox-<key> container the host starts through the Docker socket on that user's first command. A sandbox holds a named volume with one folder per agent, and bash there runs as an unprivileged agent user with a clean environment. Pilot's deployment sets MASH_SANDBOX_MOUNTS so each sandbox also gets the mashpy checkout, read-only, at /home/agent/mashpy. The agents read the repository as it is on disk, and an edit shows up without a restart.

The pilot agent

The pilot agent registers an AskUserTool and gets bash from the host, like every agent on a host with sandboxes. Its prompt carries a map of where things are documented (CLAUDE.md, each module's README.md and AGENTS.md, the posts, the H2A RFC) rather than the documents themselves. It finds the answer with rg, reads the lines it needs with sed, and cites them as path:line. When the user asks for an app, it delegates to the builder.

The builder agent

The builder builds each app in its own directory under /home/agent/workspaces/builder/apps in the user's sandbox. It loads the matching skill, creates the project with uv init, installs mashpy with uv add, and writes the files. It checks the result by importing the pool and running the app's tests, and replies with the directory, the files, and the check output. The sandbox's volume outlives the container, so the apps survive a sandbox being stopped or replaced. The builder cannot serve what it builds, because a sandbox has no Docker; the user copies the app out with docker cp.

Workflows

pilot-changelog shows the mixed-step shape. A CodeStep reads CHANGELOG.md and slices out the most recent release section(s) in deterministic Python, then an AgentStep summarizes that excerpt, reaching into the source with bash only when an entry is too terse to explain. The code step runs on the host, which mounts the checkout at the same path. Its ChangelogSummarizerSpec rides the agent_spec path, so registering the workflow registers the summarizer as a workflow-only agent with its own process. /workflow run pilot-changelog runs it from the REPL.

# pilot/catalog/workflows/changelog.py
def build_changelog_workflow_spec(repo_root: Path = REPO_ROOT) -> WorkflowSpec:
    return WorkflowSpec(
        workflow_id="pilot-changelog",
        input_model=ChangelogIn,
        steps=[
            CodeStep(
                step_id="read-changelog",
                run=_make_read_changelog(repo_root),
                input=ChangelogIn,
                output=ChangelogExtract,
            ),
            AgentStep(
                step_id="summarize",
                agent_spec=ChangelogSummarizerSpec(repo_root),
                input=ChangelogExtract,
                output=ChangelogSummary,
            ),
        ],
    )

Deployment

Pilot runs from a checkout with Docker Compose: Postgres and the host, on a network named mash. The host container mounts the Docker socket so it can start the sandboxes, and reads GEMINI_API_KEY, OPENROUTER_API_KEY and MASH_HOST_SECRET from .env.

git clone https://github.com/imsid/mashpy.git && cd mashpy
docker compose -f docker-compose.pilot.yml up -d --build

The CLI installs separately and points at any running store by URL.

curl -fsSL https://raw.githubusercontent.com/imsid/mashpy/main/install.sh | sh
mash connect --api-base-url http://127.0.0.1:8000 --user-id me
pilot browse                  # see the catalog
pilot repl --host guide       # enter the default composition

The admin dashboard is available at /admin on the running host. It shows the pool, active host compositions, and agent traces with a span tree drawer.

Adding an agent to the catalog

A new catalog entry is a new package under pilot/catalog/agents/ plus one CatalogEntry in CATALOG. The host handles pool registration, the agent's process, the store listing, delegation, sessions and streaming.

1
Create pilot/catalog/agents/my_agent/spec.py. Subclass AgentSpec and implement get_agent_id(), build_tools(), build_skills(), build_llm(), and build_agent_config(). Add a build_metadata() function returning AgentMetadata.
2
Add a CatalogEntry to CATALOG in pilot/catalog/__init__.py.
3
Rebuild with docker compose -f docker-compose.pilot.yml up -d --build. The host starts the new agent's process, and the agent appears in pilot browse.
4
Compose it into a host: pilot compose my-host --primary pilot --subagents my-agent. Enter: pilot repl --host my-host.
The stock mash CLI speaks the same protocol as pilot. mash connect --api-base-url http://127.0.0.1:8000 then mash repl --agent builder opens a direct REPL against any catalog agent, bypassing the store CLI. This is useful for debugging a new agent before composing it into a host.
